Hour 1–4 · Functions & scope · Lambda · Map/Filter · Nested functions · Files · Exceptions

Functions — What They Are and Why They Exist Hour 2

Start from the everyday idea. Imagine you had to explain, from scratch, how to make a cup of tea, every single time someone wanted one — boil water, add tea, wait, add milk, pour. That's exhausting. Instead you'd write the instructions down once, label them "Make Tea," and from then on just say "make tea" whenever you want one. A function is exactly that label: a named, reusable block of instructions you write once and can "call" (run) as many times as you like, with different details each time if you want (e.g. "make tea, but with 2 sugars").

Why this matters in code. Without functions, a program is one long list of steps from top to bottom — and if you need to repeat a calculation five times, you'd have to copy-paste it five times. If you later find a bug in that calculation, you now have to fix it in five places. Functions collapse that into one place: fix it once, and everywhere that calls the function is automatically fixed.

Anatomy of a function, piece by piece:

def make_tea(sugars):
    print(f"Boiling water...")
    print(f"Adding tea and {sugars} sugar(s)...")
    print("Tea is ready!")

# calling (running) the function twice, with different input
make_tea(2)
make_tea(0)
  • def — the keyword that says "I am about to define a function."
  • make_tea — the name you'll use to call it later.
  • (sugars) — the parameter: a placeholder for a value the caller will supply. When you call make_tea(2), 2 is the argument — the actual value plugged into that placeholder.
  • The indented lines below def are the function's body — what actually runs when it's called.
Common beginner confusion "Parameter" and "argument" are often used interchangeably in casual speech, but technically: the parameter is the name in the function's definition (sugars); the argument is the actual value you pass in when calling it (2).

Returning a value. So far our function only prints — it doesn't hand back a result the rest of the program can use. That's what return is for:

def add_numbers(a, b):
    result = a + b
    return result   # hands the value back to whoever called this function

total = add_numbers(4, 7)   # total now holds 11
print(total)

Default arguments. You can give a parameter a fallback value, used only if the caller doesn't supply one — moving from beginner usage toward more flexible, real-world function design:

def make_tea(sugars=1):     # default: 1 sugar if not specified
    print(f"Tea with {sugars} sugar(s)")

make_tea()      # uses the default → "Tea with 1 sugar(s)"
make_tea(3)     # overrides the default → "Tea with 3 sugar(s)"
Why companies use this Every reusable piece of a real ML pipeline — a data-cleaning step, a model-training routine, an API endpoint — is a function. Functions are the smallest unit of reusable, testable logic in almost every programming language.

Functions and Variable Scope Hour 2

The core idea, in plain words. A variable created inside a function only exists inside that function — like a conversation that happens in a closed meeting room and stays in that room. This "visibility zone" is called scope.

def calculate():
    result = 42      # 'result' is LOCAL to this function
    print(result)     # works fine — we're inside the room

calculate()
print(result)          # NameError! 'result' doesn't exist out here

Global scope is the opposite: a variable created at the top level of your script (outside any function) can be read from inside any function below it:

course_name = "AI & ML"    # global variable

def greet():
    print(f"Welcome to {course_name}")   # can READ the global

greet()
Common mistake You can read a global variable inside a function freely, but if you try to assign to a variable with the same name inside a function, Python assumes you meant a new local variable — unless you explicitly say global course_name first. This trips up almost every beginner at least once.

Advanced note: Python looks up a name using the "LEGB" rule — Local, then Enclosing (an outer function, if any), then Global, then Built-in. You don't need to memorize this yet; just know that Python always searches from the innermost scope outward.

Lambda Expressions Hour 2

Start simple. A lambda is just a function written in one line, with no name (an "anonymous" function) — useful for small, throwaway operations you don't need to reuse elsewhere.

# a normal function...
def square(n):
    return n * n

# ...and the same thing as a lambda
square_lambda = lambda n: n * n

print(square(5))          # 25
print(square_lambda(5))   # 25

Read lambda n: n * n as: "a function that takes n and returns n * n." Lambdas are almost never assigned to a variable like above in real code — their real use is being passed directly into another function, which is exactly what map and filter below need.

Map and Filter Hour 2

Map — "apply this to every item." Imagine a factory conveyor belt where every item passes through the same machine and comes out transformed. map() applies one function to every element of a list and gives you back the transformed results.

prices = [100, 250, 80, 500]

# add 10% tax to every price
with_tax = list(map(lambda p: p * 1.10, prices))
print(with_tax)   # [110.0, 275.0, 88.0, 550.0]

Filter — "keep only what passes the test." Imagine a sieve: only items matching a condition fall through and survive; the rest are discarded.

ages = [15, 22, 17, 30, 12, 45]

# keep only ages 18 and above
adults = list(filter(lambda a: a >= 18, ages))
print(adults)   # [22, 30, 45]
Beginner-friendly equivalent Everything map and filter do, a list comprehension (from Week 1) can also do, often more readably: [p * 1.10 for p in prices] and [a for a in ages if a >= 18]. Learn both — you'll see map/ filter in older codebases and interview questions, but comprehensions are the more idiomatic modern style.

Inner / Nested Functions Hour 2

A function can be defined inside another function. The inner function is only visible inside the outer one — useful when a small helper step is only ever needed by one specific function and shouldn't clutter the rest of your file.

def process_order(items):
    def calculate_total(items):        # inner helper, private to process_order
        return sum(items)

    total = calculate_total(items)
    print(f"Order total: {total}")

process_order([10, 20, 30])
# calculate_total([1,2]) here would fail — it doesn't exist outside process_order

File Handling Hour 4

Why this matters immediately. Every dataset you'll load in this course — CSV files of housing prices, text files of tweets, image files for computer vision — starts with opening a file from disk. Python's open() function is the doorway.

# writing to a file — "w" mode creates it (or overwrites it) fresh
with open("notes.txt", "w") as f:
    f.write("Week 2: OOP and Statistics\n")

# reading it back — "r" mode
with open("notes.txt", "r") as f:
    content = f.read()
    print(content)

# appending — "a" mode adds to the end without erasing existing content
with open("notes.txt", "a") as f:
    f.write("Adding another line.\n")

# reading line by line — memory-efficient for huge files
with open("notes.txt", "r") as f:
    for line in f:
        print(line.strip())
Best practice Always use with open(...) as f: rather than calling open() and close() manually. The with block automatically closes the file even if an error happens inside it — a very common source of subtle bugs otherwise.

Exception Handling Hour 4

The everyday analogy. When you try a risky action — like opening a locked door — you might have a backup plan ready ("if it's locked, use the spare key") instead of the whole plan collapsing. An exception is Python's way of signaling "this specific thing went wrong," and try/except is your backup plan.

try:
    age = int(input("Enter your age: "))
    print(f"You are {age} years old")
except ValueError:
    print("That wasn't a valid number — please enter digits only.")

Building up: you can catch different error types differently, run cleanup code no matter what happened with finally, and even define your own custom error types for advanced programs:

try:
    file = open("missing_file.txt")
    number = 10 / 0
except FileNotFoundError:
    print("The file doesn't exist.")
except ZeroDivisionError:
    print("Cannot divide by zero.")
finally:
    print("This always runs — cleanup, logging, closing connections, etc.")

# custom exception — advanced, but common in real ML pipelines
class InvalidDatasetError(Exception):
    pass

def load_dataset(rows):
    if len(rows) == 0:
        raise InvalidDatasetError("Dataset is empty!")
    return rows
Common mistake Writing a bare except: with nothing after it catches every possible error, including ones you didn't anticipate — this hides real bugs. Always name the specific exception type you expect, like except ValueError:.

Classes, Objects & Inheritance

Hour 1–4 · Classes & objects · Constructors · Inheritance types · Access specifiers · Composition

Classes and Objects — The Big Idea Hour 1

Forget code for a second. Think about the concept "Car." There's no single physical car called "Car" — it's a blueprint describing what any car has (wheels, color, engine size) and what any car can do (start, stop, accelerate). Your actual red Toyota in the driveway is one specific, real instance built from that blueprint. In programming: the blueprint is a class, and each real thing built from it is an object (also called an "instance").

Why we need this at all. Up to now you've stored data in loose variables and lists. But real-world things have both data (a student's name and grade) and behavior (a student can enroll, submit an assignment). Object-Oriented Programming (OOP) bundles data and behavior that belong together into one unit — instead of having them scattered across separate lists and functions that have to be kept in sync by hand.

class Student:
    def __init__(self, name, grade):   # the constructor — more below
        self.name = name                 # instance variable — this student's own name
        self.grade = grade

    def greet(self):                    # an instance method — a behavior
        print(f"Hi, I'm {self.name} and I'm in grade {self.grade}")

# building two real objects from the one blueprint
student1 = Student("Ayesha", 10)
student2 = Student("Bilal", 9)

student1.greet()   # "Hi, I'm Ayesha and I'm in grade 10"
student2.greet()   # "Hi, I'm Bilal and I'm in grade 9"
What is self? self is how a method refers to "the specific object I was called on." When you run student1.greet(), Python automatically passes student1 in as self — that's how greet() knows to print Ayesha's name and not Bilal's, even though it's the exact same method code for both objects.

Instance Variables & Methods vs. Class Variables & Methods Hour 1

Instance variables (like self.name above) belong to one specific object — Ayesha's name is separate from Bilal's name. Class variables are shared by every object built from that class — think of a school's name, which is the same for every student regardless of which student you ask.

class Student:
    school_name = "NAVTTC Institute"   # CLASS variable — shared by ALL students

    def __init__(self, name):
        self.name = name                 # INSTANCE variable — unique per student

s1 = Student("Ayesha")
s2 = Student("Bilal")

print(s1.school_name)   # "NAVTTC Institute"
print(s2.school_name)   # "NAVTTC Institute" — same, shared value
print(s1.name, s2.name) # "Ayesha Bilal" — different, per-object values

Similarly, a normal method (decorated with nothing, taking self) operates on one object's data, while a @classmethod (taking cls) operates on the class itself, and a @staticmethod is just a regular function that happens to live inside the class for organizational purposes, needing neither self nor cls.

Constructors and Destructors Hour 1

The constructor, __init__, runs automatically the moment an object is created — it "constructs" the object by setting up its starting data (exactly like filling in a form the instant you create a new account). The destructor, __del__, runs automatically right before an object is destroyed / garbage collected — useful for cleanup like closing a file or a database connection.

class DatabaseConnection:
    def __init__(self, name):
        self.name = name
        print(f"Opening connection: {name}")

    def __del__(self):
        print(f"Closing connection: {self.name}")

conn = DatabaseConnection("training_db")
del conn   # explicitly triggers __del__ → "Closing connection: training_db"
Advanced note In real production code, don't rely on __del__ for critical cleanup like closing files — its exact timing isn't guaranteed. Prefer the with statement pattern from Day 1's file handling section instead.

Inheritance — Reusing a Blueprint Hour 2–3

Everyday analogy. A "Sports Car" and a "Family Car" are both still cars — they share everything a general Car has (wheels, engine, the ability to start) but each adds or changes something specific. Rather than rewriting "Car" from scratch for each, you'd say "Sports Car is a Car, but faster." Inheritance lets one class (the child / subclass) automatically get everything from another class (the parent / superclass), then add or override only what's different.

class Animal:                        # parent / base class
    def __init__(self, name):
        self.name = name
    def speak(self):
        print(f"{self.name} makes a sound")

class Dog(Animal):                    # Dog INHERITS from Animal
    def speak(self):                   # overriding the parent's method
        print(f"{self.name} barks")

d = Dog("Rex")
d.speak()   # "Rex barks" — Dog's own version, not Animal's

Multilevel inheritance — a chain, grandparent → parent → child, where each level builds on the one before:

class Animal:
    def eat(self): print("eating")

class Mammal(Animal):        # Mammal inherits from Animal
    def breathe(self): print("breathing air")

class Dog(Mammal):            # Dog inherits from Mammal, which inherits from Animal
    def bark(self): print("barking")

d = Dog()
d.eat(); d.breathe(); d.bark()   # Dog has ALL three abilities

Hierarchical inheritance — the reverse shape: one parent, many children, each specializing differently:

class Vehicle:
    def move(self): print("moving")

class Car(Vehicle): pass
class Bike(Vehicle): pass
class Truck(Vehicle): pass
# Car, Bike, and Truck all separately inherit from the same Vehicle

Multiple inheritance — one child, multiple parents at once (Python allows this, unlike many languages):

class Flyer:
    def fly(self): print("flying")

class Swimmer:
    def swim(self): print("swimming")

class Duck(Flyer, Swimmer):   # Duck inherits from BOTH
    pass

d = Duck()
d.fly(); d.swim()
Method Resolution Order (MRO) When two parents define the same method name, which one wins? Python answers this with the Method Resolution Order — a defined left-to-right, depth-first search order. You can inspect it yourself: print(Duck.__mro__). This becomes important once your class hierarchies get deep — a genuinely advanced topic worth revisiting once you're comfortable with basic inheritance.

Access Specifiers: Public, Protected, Private Hour 4

The idea, before the syntax. Not every piece of data inside an object should be freely editable from outside. A bank account object shouldn't let outside code just set balance = -999999 directly — it should go through a controlled method. Access specifiers are the language's way of marking "this is meant to be used from outside" versus "this is internal, don't touch."

class BankAccount:
    def __init__(self, balance):
        self.balance = balance           # public — freely accessible
        self._pin_attempts = 0            # protected (convention: single underscore)
        self.__account_number = "12345"   # private (double underscore)

acc = BankAccount(1000)
print(acc.balance)            # fine — public
print(acc._pin_attempts)       # works, but the underscore SIGNALS "internal use only"
# print(acc.__account_number)   -> AttributeError, name-mangled (see below)
  • Public (no underscore) — intended for free use from outside the class.
  • Protected (single underscore _name) — a convention, not enforced by Python, meaning "internal — subclasses may use this, but outside code shouldn't."
  • Private (double underscore __name) — Python actively makes this harder to access from outside via name mangling.
Name Mangling explained Python internally renames __account_number to _BankAccount__account_number. It's still technically reachable if you know the mangled name, so this is "strong discouragement," not a hard lock — Python trusts developers more than it enforces rules, which is a real difference from languages like Java.

Inner/Nested Classes Hour 4

Just like a nested function, a class can be defined inside another class — used when one class only makes sense as a small supporting detail of another.

class Car:
    class Engine:                 # nested class — an Engine only makes sense inside a Car
        def start(self):
            print("Engine starting...")

    def __init__(self):
        self.engine = self.Engine()

my_car = Car()
my_car.engine.start()

Association, Aggregation & Composition Hour 4

These describe how two classes relate to each other — moving from a loose connection to a tight one:

  • Association — the loosest link: two independent objects that simply know about or use each other, e.g. a Teacher and a Student. Each can exist perfectly well without the other.
  • Aggregation — a "has-a" relationship where the part can still exist independently of the whole, e.g. a Department "has" Professors, but a professor still exists if the department is dissolved.
  • Composition — the tightest "has-a": the part cannot exist without the whole, e.g. a House "has" Rooms — a room stops existing conceptually if the house is torn down.
# Composition example — Engine cannot meaningfully exist without a Car owning it
class Engine:
    def start(self): print("Vroom")

class Car:
    def __init__(self):
        self.engine = Engine()   # Car OWNS and CREATES its own Engine

    def start_car(self):
        self.engine.start()

Polymorphism & Advanced OOP

Hour 1–4 · Polymorphism & operator overloading · Dunder methods · Dynamic polymorphism · Abstract & data classes · Keyword arguments

Polymorphism and Operator Overloading Hour 1

The word, unpacked. "Poly" = many, "morph" = form. Polymorphism means "the same action name behaves differently depending on what it's used on." You already use this constantly without noticing: + adds two numbers, but also joins two strings. Same symbol, different behavior depending on the type. That's polymorphism baked right into Python's own operators.

print(3 + 4)          # 7 — numeric addition
print("AI" + "ML")    # "AIML" — string concatenation

Operator overloading means teaching your own class how +, ==, or other operators should behave when used on your objects — you're extending this same idea of "the same symbol, new meaning" to types you define yourself.

class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):          # teaches Python what + means for Points
        return Point(self.x + other.x, self.y + other.y)

    def __repr__(self):
        return f"Point({self.x}, {self.y})"

p1 = Point(1, 2)
p2 = Point(3, 4)
print(p1 + p2)   # Point(4, 6) — our own custom '+' behavior

Magic Functions / Dunder Methods Hour 2

__add__ above is one example of a wider family called dunder methods (short for "double underscore") or "magic methods" — special names Python automatically calls behind the scenes to make your objects work naturally with built-in syntax like +, len(), print(), and comparisons.

class Book:
    def __init__(self, title, pages):
        self.title = title
        self.pages = pages

    def __str__(self):                  # controls what print(book) shows
        return f"'{self.title}' ({self.pages} pages)"

    def __len__(self):                  # controls what len(book) returns
        return self.pages

    def __eq__(self, other):            # controls what book1 == book2 checks
        return self.pages == other.pages

b1 = Book("Python Basics", 250)
print(b1)          # 'Python Basics' (250 pages) — uses __str__
print(len(b1))     # 250 — uses __len__
Why this matters Every time you've called print(some_object) and gotten a readable sentence instead of <object at 0x7f...>, a dunder method was doing that work. You'll define __init__, __str__, and sometimes __len__ or __eq__ on almost every custom class you write from here on.

Dynamic Polymorphism (Subclass as Base Class) Hour 3

This is the classic OOP idea: you can treat a child object as if it were its parent type, and the correct, specific version of a method still runs automatically — decided at runtime, hence "dynamic."

class Shape:
    def area(self):
        return 0

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2

class Square(Shape):
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2

shapes = [Circle(3), Square(4)]     # a list of the PARENT type, holding different children
for shape in shapes:
    print(shape.area())              # each calls ITS OWN version of area() automatically
Real world application This is exactly the pattern behind scikit-learn's models: LinearRegression, RandomForestClassifier, and dozens of others all share a common .fit() and .predict() interface, so the same training loop code works no matter which specific model object you pass into it.

Abstract Method & Class, Empty Class, Data Class Hour 4

Abstract class. Sometimes you want to define a blueprint that cannot be used directly — only its children can — because it doesn't make sense on its own. "Shape" alone has no area formula; only specific shapes do. Python enforces this with the abc module:

from abc import ABC, abstractmethod

class Shape(ABC):                 # ABC = Abstract Base Class
    @abstractmethod
    def area(self):                # no implementation — children MUST provide one
        pass

# shape = Shape()  -> TypeError: Can't instantiate abstract class

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2   # required implementation

c = Circle(2)
print(c.area())

Empty class — sometimes you just need a simple namespace/placeholder with no behavior yet:

class Placeholder:
    pass

p = Placeholder()
p.note = "filled in later"   # you can still attach attributes dynamically

Data class — a modern, less repetitive way to write classes that mostly just hold data, auto-generating __init__ and __repr__ for you:

from dataclasses import dataclass

@dataclass
class Student:
    name: str
    grade: int

s = Student("Ayesha", 10)
print(s)   # Student(name='Ayesha', grade=10) — auto-generated, no __init__ written by hand

Keyword Arguments Hour 4

So far you've called functions by position: make_tea(2) means "2 goes into the first parameter." A keyword argument instead names which parameter you mean, so order stops mattering and the call becomes self-documenting:

def create_profile(name, age, country):
    print(f"{name}, {age}, from {country}")

# positional — order-dependent, easy to mix up
create_profile("Ayesha", 20, "Pakistan")

# keyword — order-independent, and much clearer to read
create_profile(age=20, country="Pakistan", name="Ayesha")

# **kwargs — a function that accepts ANY number of keyword arguments
def show_settings(**kwargs):
    for key, value in kwargs.items():
        print(key, "=", value)

show_settings(learning_rate=0.01, epochs=10, batch_size=32)

Types of Data & Measures of Central Tendency

Hour 1–4 · Structured/unstructured data · Quantitative & qualitative variables · Mean, median, mode

Why we're switching gears. The next two days move from "how do I write code" to "how do I describe a real pile of numbers in words a decision-maker can understand." This is statistics — and every idea below is something you already do informally in daily life (like knowing your "typical" commute time); we're just going to make it precise and give it a name.

Structured vs. Unstructured Data Hour 1

Structured data fits neatly into rows and columns, like a spreadsheet or a database table — every entry has a clear, predictable place: a "Name" column, an "Age" column, a "City" column. It's easy for a computer to search and calculate on directly.

Unstructured data has no such fixed shape — a photo, a voice recording, a free-form customer review, a PDF. A computer can't directly compute "the average" of a set of photos the way it can average a column of numbers; unstructured data usually needs to be converted into structured, numeric form first (this conversion is a huge part of what Machine Learning and Deep Learning, later in this course, actually do).

Real world example A hospital's patient records table (name, age, blood pressure) is structured. The X-ray images and doctors' handwritten notes attached to that same patient are unstructured.

Quantitative Data — Numerical, Continuous, Discrete Hour 1–2

Quantitative data is anything you can meaningfully do arithmetic on — it answers "how much" or "how many." It splits into two further beginner-friendly categories:

  • Discrete — countable in whole, separate steps; you can list every possible value. Number of children in a family (0, 1, 2, 3...) — you can never have 2.5 children.
  • Continuous — can take any value within a range, including fractions, limited only by how precisely you measure. Height (170.2 cm, 170.23 cm, 170.234 cm...) — there's always a finer measurement possible.
Quick test you can apply yourself Ask: "could this value ever be a fraction and still make sense?" Number of students in a class → no → discrete. Temperature in a room → yes (22.6°C) → continuous.

Qualitative Data — Categorical, Nominal, Ordinal, Binary Hour 1–2

Qualitative (categorical) data describes a quality or category rather than an amount — it answers "what kind," not "how much." You can't meaningfully average it. It splits further:

  • Nominal — categories with no natural order: eye color (blue, brown, green), country of birth, blood type. "Blue" isn't "more" or "less" than "brown," they're just different.
  • Ordinal — categories that DO have a meaningful order, but the gaps between them aren't precisely measurable: a satisfaction survey (poor, fair, good, excellent) or education level (high school, bachelor's, master's). "Excellent" is clearly better than "poor," but we can't say it's exactly "3 units better."
  • Binary — exactly two possible categories: yes/no, pass/fail, true/false, spam/not-spam. This special case shows up constantly in ML as the target for a "classification" model.
Common mistake Encoding a nominal category as numbers (red=1, blue=2, green=3) for a computer to use can accidentally imply a false order or false distance ("is blue really halfway between red and green?"). This is a genuinely important, easy-to-miss trap you'll return to when you reach data preprocessing for Machine Learning in Week 4–5.

Measures of Central Tendency — Mean, Median, Mode Hour 3–4

The plain-language question these answer: "If I had to describe this whole list of numbers using just ONE typical number, what would it be?" There are three honest answers, each useful in different situations.

Mean (the "average"). Add up every value, divide by how many values there are. This is the one most people already call "average."

scores = [70, 85, 90, 60, 95]
mean = sum(scores) / len(scores)
print(mean)   # 80.0
Common mistake — the mean's weak spot The mean is easily pulled off-center by one extreme value ("outlier"). If nine people earn $50,000 and one person earns $5,000,000, the mean salary looks huge and misleading — it no longer represents a "typical" person in that group.

Median (the true middle). Sort every value in order, and pick the exact middle one (or the average of the two middle ones if there's an even count). The median isn't dragged around by extreme values the way the mean is — which is exactly why "median household income," not mean, is the number governments usually report.

salaries = [50000, 52000, 51000, 53000, 5000000]
sorted_salaries = sorted(salaries)   # [50000, 51000, 52000, 53000, 5000000]
median = sorted_salaries[2]           # the middle (3rd of 5) value → 52000
print(median)   # 52000 — much more "typical" than the mean would be here

Mode (the most frequent value). Simply, whichever value appears most often. It's the only one of the three that also works for qualitative/categorical data (you can't take the "mean" of favorite colors, but you can find the most common one).

favorite_colors = ["blue", "red", "blue", "green", "blue", "red"]
# "blue" appears 3 times — more than any other color
# mode = "blue"

from statistics import mean, median, mode
print(mean([70, 85, 90, 60, 95]))     # 80
print(median([70, 85, 90, 60, 95]))    # 85
print(mode(["blue","red","blue","green"]))  # 'blue'
How to choose which one to report Use the mean for symmetric numeric data with no extreme outliers. Use the median when outliers or skew are present (income, house prices, response times). Use the mode for categorical data, or to answer "what's the single most common thing."

Measures of Dispersion & Position

Hour 1–4 · Variance, std. deviation, coefficient of variation, skewness, kurtosis · Z-score, percentile, quartile

Why We Need More Than Just "the Typical Value" Hour 1

Two classes could both have a mean score of 75 — but in one class, everyone scored between 70–80, and in the other, scores ranged wildly from 20–100. The mean alone hides this difference completely. Dispersion (also called "spread" or "variability") measures how bunched-together or how scattered the data is around its center — arguably just as important as the center itself.

Variance and Standard Deviation Hour 1–2

Building the idea step by step. To measure "how spread out," a natural first instinct is: for each value, find its distance from the mean, then average those distances. There's a catch — some distances are negative (below the mean) and some positive (above), and they'd cancel out to roughly zero if we just averaged them directly. The fix: square each distance first (which also always makes it positive), then average those squared distances. That average is called the variance.

scores = [70, 85, 90, 60, 95]
mean = sum(scores) / len(scores)                       # 80.0
squared_diffs = [(x - mean) ** 2 for x in scores]
variance = sum(squared_diffs) / len(scores)
print(variance)   # 176.0
Why variance alone is awkward Because we squared the distances, variance is in "squared units" — if your data is in dollars, variance is in "dollars squared," which isn't intuitive to reason about directly.

Standard deviation fixes exactly that: it's simply the square root of the variance, bringing the units back to something directly comparable to the original data (dollars, not dollars-squared). It's the single most commonly reported spread measure in statistics.

import math
std_dev = math.sqrt(variance)
print(std_dev)   # ≈ 13.27

# or, using the built-in statistics module directly:
from statistics import variance, stdev
print(variance(scores))
print(stdev(scores))
Intuition to keep A small standard deviation means values cluster tightly around the mean (consistent, predictable). A large standard deviation means values are scattered widely (inconsistent, less predictable) — this single number is why "risk" in finance is so often measured with standard deviation of returns.

Coefficient of Variation Hour 1–2

The problem it solves. A standard deviation of "5" is huge if the mean is 10, but tiny if the mean is 10,000 — you can't fairly compare the "spread" of two different datasets using raw standard deviation alone if their scales differ wildly. The coefficient of variation (CV) fixes this by expressing standard deviation as a percentage of the mean, making spread comparable across totally different scales.

cv = (std_dev / mean) * 100
print(cv)   # ≈ 16.6% — spread relative to the average, as a percentage
Real world example Comparing the volatility of a stock priced around $5 versus one priced around $500 by raw standard deviation alone is misleading; comparing their coefficients of variation gives a fair, scale-independent comparison of relative risk.

Skewness and Kurtosis Hour 1–2

Skewness describes whether your data leans lopsided to one side of the mean rather than being symmetric. Picture a histogram (a bar chart of how often each value range occurs):

  • Symmetric (skewness ≈ 0) — a balanced, mirror-image shape, like classic exam scores clustering around an average.
  • Right-skewed / positive skew — a long tail stretching to the right; most values are low/moderate but a few very high ones pull the tail out (classic example: household income, where most people earn moderate amounts but a few earn enormous amounts).
  • Left-skewed / negative skew — the mirror opposite, a long tail stretching left (example: age at retirement, where most people retire in a narrow late-career range but a few retire very young).

Kurtosis describes how "heavy-tailed" or "peaked" the distribution is compared to a standard bell curve — in plain terms, how likely extreme outliers are. High kurtosis means more frequent extreme values than a normal bell curve would predict (relevant in finance for estimating the real risk of rare, extreme market crashes).

from scipy.stats import skew, kurtosis
data = [70, 85, 90, 60, 95, 100, 100, 98]
print(skew(data))
print(kurtosis(data))

Measures of Position — Z-Score, Percentile, Quartile Hour 3–4

The question these answer: "Given one single value, where does it stand relative to the rest of the data?" — not the shape of the whole dataset, but the position of one point within it.

Z-score answers "how many standard deviations away from the mean is this one value?" It converts any raw value into a universal, comparable unit.

z = (x - mean) / std_dev

# example: your exam score is 92, class mean is 80, std dev is 10
z_score = (92 - 80) / 10
print(z_score)   # 1.2 → your score is 1.2 standard deviations above average
Why this is powerful A Z-score lets you compare values from totally different scales fairly — e.g. "was my SAT score of 1400 or my friend's IELTS score of 8 more impressive relative to their own distributions?" Z-scores make that an apples-to-apples comparison.

Percentile tells you what fraction of the data falls below a given value. "You scored in the 90th percentile" means 90% of everyone else scored lower than you.

Quartiles are just three specific, especially useful percentiles that split the data into four equal quarters:

  • Q1 (25th percentile) — 25% of values fall below this point.
  • Q2 (50th percentile) — this is just the median again, the halfway point.
  • Q3 (75th percentile) — 75% of values fall below this point.
import numpy as np
data = [55, 60, 65, 70, 75, 80, 85, 90, 95, 100]

q1 = np.percentile(data, 25)
q2 = np.percentile(data, 50)   # same as the median
q3 = np.percentile(data, 75)
print(q1, q2, q3)
Advanced note — the IQR Q3 - Q1 is called the Interquartile Range (IQR) — the spread of just the "middle 50%" of your data, ignoring extreme values entirely. It's the standard tool for flagging outliers: any value more than 1.5×IQR below Q1 or above Q3 is typically treated as an outlier worth investigating, a technique you'll use constantly once you reach data cleaning in Week 4.
